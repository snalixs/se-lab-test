# ระบบโพสต์: การมองเห็น คอมเมนต์ และการเก็บโพสต์ที่ลบ

รัน `go run . -migrate` จาก `backend` แล้วเปิด API ใหม่ เพื่อใช้ migration
`003_comment_editing.sql` และ `004_post_archive.sql` ไม่ต้องรันไฟล์ใน handoff/sql
ซ้ำกับฐานข้อมูลเดิม ไฟล์ handoff ใช้สำหรับสร้าง schema ใหม่เท่านั้น

## การมองเห็น

ตอนสร้างโพสต์เลือก `visibility` เป็น `public` หรือ `followers` ได้ทั้ง JSON และ
multipart/form-data ถ้าไม่ส่งจะใช้ public ตามพฤติกรรมเดิม เจ้าของเห็นโพสต์ตนเอง
ส่วน followers ต้องเป็นผู้ติดตามเจ้าของใน user_follows ผู้ใช้ทุกคนยังต้องผ่าน
การยืนยันตัวตนของ API แม้โพสต์เป็น public แชร์ได้เฉพาะโพสต์ public ที่ยังอยู่

## คอมเมนต์

- `PATCH /api/posts/{post}/comments/{comment}` รับ `{"content":"ข้อความใหม่"}`
  แก้ได้เฉพาะผู้เขียน ข้อความหลังตัดช่องว่างต้องยาว 1–350 ตัวอักษร
- `DELETE /api/posts/{post}/comments/{comment}` ลบได้เฉพาะผู้เขียนเช่นกัน
  เจ้าของโพสต์ไม่มีสิทธิ์แก้ไขหรือลบคอมเมนต์ของคนอื่นผ่าน API นี้
- ต้องยังมีสิทธิ์เข้าถึงโพสต์นั้น และ comment ต้องอยู่ใน post ที่ระบุ
- เพิ่ม `comments.updated_at` ว่างได้ ก่อนแก้ไขครั้งแรกเป็น NULL
- เมื่อลบคอมเมนต์ คำตอบของคนอื่นยังอยู่ โดยเปลี่ยน parent_comment_id เป็น NULL
  การลบคอมเมนต์เดี่ยวไม่ได้เก็บสำรองใน deleted_posts
- การแก้ไขและลบสำเร็จตอบ 204 ส่วนรายการที่ไม่มีหรือไม่ใช่ของผู้เรียกตอบ 404

## ลบโพสต์และสำรองข้อมูล

`DELETE /api/posts/{post}` ทำงานเฉพาะเจ้าของโพสต์ใน transaction เดียว:

1. ล็อกโพสต์เพื่อไม่ให้ข้อมูลที่เกี่ยวข้องเปลี่ยนระหว่างสำรอง
2. บันทึกลง `deleted_posts`
3. เปลี่ยนโพสต์แชร์ให้ชี้ว่าต้นฉบับถูกลบ โดยเก็บข้อความและปฏิสัมพันธ์ของโพสต์แชร์ไว้
4. ลบแถวต้นฉบับจาก posts รวมถึงข้อมูลลูกผ่าน foreign keys

ถ้าสำรองล้มเหลวจะ rollback และไม่ลบต้นฉบับ การเรียกลบซ้ำโดยเจ้าของตอบ 204
และไม่สร้างสำเนาซ้ำ ไม่มี endpoint อ่านหรือกู้คืน archive สำหรับผู้ใช้ทั่วไป

| คอลัมน์ใน deleted_posts | ความหมาย |
|---|---|
| id | PK ของรายการสำรอง |
| original_post_id | ID โพสต์เดิม ไม่ซ้ำ |
| author_id | ผู้เขียนเดิม |
| deleted_by | ผู้สั่งลบ |
| deleted_at | เวลาลบ |
| snapshot_version | เวอร์ชันรูปแบบข้อมูลสำรอง ปัจจุบัน 1 |
| post_data | JSONB ของแถว posts ก่อนลบ |
| related_data | JSONB ของ images, comments, likes, bookmarks และ hashtags |

ID ใน archive ไม่มี FK ไปยังตารางใช้งาน เพื่อให้ข้อมูลสำรองอยู่ได้แม้ต้นฉบับ
ถูกลบ รูปภาพสำรองเฉพาะ metadata/URL ไฟล์รูปใน media ยังคงอยู่ที่เดิม ไม่ได้
ถูกย้ายหรือลบ และเส้นทาง media เดิมยังเปิดได้โดยผู้ที่มีลิงก์ จึงยังควรสำรอง
ฐานข้อมูลและโฟลเดอร์ media ด้วยสคริปต์ backup ตามปกติ ตาราง archive นี้ไม่ได้
ทดแทน backup ทั้งระบบ และยังไม่มีนโยบายล้างข้อมูล archive อัตโนมัติ

โพสต์ที่มี status=deleted จากระบบเก่าไม่ถูกย้ายเองระหว่าง migration
หากเจ้าของเรียก DELETE อีกครั้งจึงจะถูกสำรองและลบจริงด้วยขั้นตอนใหม่

## โพสต์แชร์ที่ต้นฉบับถูกลบ

เพิ่ม `posts.deleted_shared_post_id` สำหรับอ้างอิง ID เดิมโดยไม่มี FK ไปยัง
posts และตั้ง shared_post_id เป็น NULL เมื่อย้ายต้นฉบับออก API ส่ง
`shared_post_deleted: true` ให้ Frontend แสดง “โพสต์ต้นฉบับถูกลบแล้ว”
โดยไม่ส่งเนื้อหาจาก archive ผู้เขียนโพสต์แชร์ยังแก้ข้อความของตนเองได้
แต่แชร์โพสต์ที่ไม่มีต้นฉบับต่ออีกไม่ได้

## การทดสอบ

`go test ./...` ทดสอบแบบไม่เชื่อม DB ส่วน integration tests ต้องตั้ง
TEST_DATABASE_URL ให้ชี้ PostgreSQL ทดสอบ แล้วรัน `go test -v ./...`
ชุดทดสอบใช้ schema ชั่วคราวชื่อ post_test_* และ group_test_* และลบเฉพาะ schema
เหล่านั้นเมื่อจบ ไม่ย้ายข้อมูลหรือล้างตารางจริง
